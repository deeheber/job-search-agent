# Requirements Document

## Introduction

Migrate the CDK stack from the experimental `@aws-cdk/aws-bedrock-agentcore-alpha` package to the stable `aws-cdk-lib/aws-bedrockagentcore` module. The migration must preserve all existing stack behavior (IAM roles, environment variables, schedules, SNS notifications, outputs) while removing the alpha dependency. The CDK version (`aws-cdk-lib` 2.257.0) remains pinned. The snapshot test file must be deleted and regenerated after migration.

## Glossary

- **CDK_Stack**: The AWS CDK stack defined in `cdk/lib/job-search-agent-stack.ts` that provisions the Job Search Agent infrastructure
- **Alpha_Module**: The experimental package `@aws-cdk/aws-bedrock-agentcore-alpha` currently used as a dependency
- **Stable_Module**: The production-ready module located at `aws-cdk-lib/aws-bedrockagentcore`
- **Package_Manifest**: The file `cdk/package.json` that declares project dependencies
- **Stack_File**: The TypeScript source file `cdk/lib/job-search-agent-stack.ts` containing stack definitions
- **Test_File**: The test file `cdk/test/cdk.test.ts` containing snapshot and assertion tests
- **Snapshot_File**: The snapshot file `cdk/test/__snapshots__/cdk.test.ts.snap` generated by vitest
- **Runtime_Construct**: The CDK construct representing an AgentCore Runtime resource
- **Artifact_Construct**: The CDK construct representing a container image artifact for the AgentCore Runtime

## Requirements

### Requirement 1: Remove Alpha Module Dependency

**User Story:** As a developer, I want the alpha package removed from the project dependencies, so that the project relies only on stable modules.

#### Acceptance Criteria

1. WHEN the migration is complete, THE Package_Manifest SHALL NOT contain any reference to `@aws-cdk/aws-bedrock-agentcore-alpha` in its `dependencies` or `devDependencies` sections.
2. WHEN the migration is complete, THE Package_Manifest SHALL retain `aws-cdk-lib` pinned at version `2.257.0` in its `dependencies` section.
3. WHEN the migration is complete, THE Package_Manifest SHALL retain all other existing dependencies and devDependencies unchanged.

### Requirement 2: Update Import Statements

**User Story:** As a developer, I want the import paths updated to the stable module, so that the stack compiles against production-ready APIs.

#### Acceptance Criteria

1. WHEN the migration is complete, THE Stack_File SHALL import the Runtime construct from `aws-cdk-lib/aws-bedrockagentcore`.
2. WHEN the migration is complete, THE Stack_File SHALL import the Artifact construct from `aws-cdk-lib/aws-bedrockagentcore`.
3. WHEN the migration is complete, THE Stack_File SHALL NOT contain any import statement referencing `@aws-cdk/aws-bedrock-agentcore-alpha`.

### Requirement 3: Adapt to Stable Module API

**User Story:** As a developer, I want the construct usage adapted to match the stable module's API surface, so that the stack synthesizes without errors.

#### Acceptance Criteria

1. WHEN the stable module renames a construct class or property compared to the Alpha_Module, THE Stack_File SHALL use the correct stable module class name or property name.
2. WHEN the stable module introduces new required properties not present in the Alpha_Module, THE Stack_File SHALL provide values for all new required properties.
3. WHEN the stable module removes a property that existed in the Alpha_Module, THE Stack_File SHALL remove usage of the removed property.
4. THE CDK_Stack SHALL synthesize a valid CloudFormation template without compilation errors after migration.

### Requirement 4: Preserve Stack Behavior

**User Story:** As a developer, I want the synthesized CloudFormation template to produce equivalent resources, so that deployed infrastructure remains unchanged.

#### Acceptance Criteria

1. THE CDK_Stack SHALL produce an `AWS::BedrockAgentCore::Runtime` resource with the same `AgentRuntimeName`, `Description`, `RoleArn`, and `EnvironmentVariables` configuration as before migration.
2. THE CDK_Stack SHALL produce the same IAM Role with trust policy for `bedrock-agentcore.amazonaws.com` and the same permission statements.
3. THE CDK_Stack SHALL produce the same CloudFormation outputs (`RuntimeId`, `RuntimeArn`, `TavilyApiKeyParameter`, `NotificationTopicArn`) with equivalent values.
4. THE CDK_Stack SHALL produce the same SNS Topic and subscription resources when `notificationEmails` are provided.
5. THE CDK_Stack SHALL produce the same EventBridge Scheduler resources when `schedules` are provided.

### Requirement 5: Regenerate Snapshot Test

**User Story:** As a developer, I want the snapshot test regenerated cleanly, so that CI passes with the new stable module output.

#### Acceptance Criteria

1. WHEN the migration is complete, THE Snapshot_File SHALL be deleted from disk.
2. WHEN the test suite is executed after deleting the Snapshot_File, THE Test_File SHALL generate a new Snapshot_File reflecting the migrated stack output.
3. THE Test_File SHALL pass all assertion tests and the snapshot test after migration.

### Requirement 6: Maintain CDK Version Pin

**User Story:** As a developer, I want the CDK version unchanged, so that the migration does not introduce unrelated dependency updates.

#### Acceptance Criteria

1. THE Package_Manifest SHALL keep `aws-cdk-lib` at exactly version `2.257.0`.
2. THE Package_Manifest SHALL NOT add any new alpha or experimental CDK packages.

### Requirement 7: Lock File Consistency

**User Story:** As a developer, I want the lock file updated to reflect the dependency change, so that installs are reproducible.

#### Acceptance Criteria

1. WHEN the Alpha_Module is removed from Package_Manifest, THE lock file (`cdk/package-lock.json`) SHALL be regenerated to exclude the Alpha_Module and its transitive dependencies.
2. THE lock file SHALL resolve all remaining dependencies without conflicts or peer-dependency warnings related to this migration.
